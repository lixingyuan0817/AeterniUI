# AeterniUI 组件计划

文档版本：`10.31.1`

文档状态：当前活动计划；只记录尚未交付的组件、能力、依赖、决策门和验收条件。

已经实现的公共能力见 [`delivered-features.zh-CN.md`](delivered-features.zh-CN.md)，已发现的质量问题见 [`review-plan.zh-CN.md`](review-plan.zh-CN.md)，已经结束的阶段和版本见 [`release-history.zh-CN.md`](release-history.zh-CN.md)。

## 1. 规划原则

- 先确认现有组件能否组合完成目标，避免重复组件和第二套交互模型。
- 先恢复已交付能力的正确性，再扩大公共组件面。
- 新组件默认只负责渲染、交互、绑定和无障碍；远程请求、缓存、分页和业务状态归宿主。
- 复杂能力先交付最小稳定公共面，不在第一版同时承诺虚拟化、拖拽、服务端查询或路由集成。
- 每项计划必须先通过 API、HTML/ARIA、Token、JS 和示例五个决策门，再进入实现。
- 本文件只记录未交付的能力，不保留已完成的计划；“暂缓/待定”必须明确标注原因和下一步决策门，不能在此处变成无证据的长期候选。

| --- | --- | --- | --- |

## 3. 新组件候选与排序（优先级 9）

定调结论：组件库优先服务**后台数据录入**场景。候选据此排序；展示与媒体类候选在本次定调下顺延，但仍保持登记。

现有能力对照（`src/AeterniUI/Components/` 与 [`delivered-features.zh-CN.md`](delivered-features.zh-CN.md)）：

- 平铺的单值与多值录入已由 `Input`、`InputNumber`、`Slider`、`Search`、`ComboBox`、`MultiSelect`、`Autocomplete` 覆盖；大列表渲染可复用 `VirtualList`。
- 浮层、焦点与键盘行为可复用 `aeterni_floating.js` 与既有 roving focus，不为候选新增第二套交互模型。
- 文件、层级数据和双列表迁移没有任何实现或等价能力：组件目录中不存在 `Upload`、`Cascader`、`Transfer`，且 `InputType` 不含 `File`。

| 顺序 | 候选 | 与现有能力的边界 | 进入实现前必须明确 |
| --- | --- | --- | --- |
| 1 | `Upload` | 库内无文件选择、校验或进度；传输、存储和协议仍归宿主 | 职责边界（组件只做选择、校验、列表与宿主驱动的进度，不定义协议）、进度与取消、错误展示、拖放与键盘模型 |
| 2 | `Cascader` | 层级数据目前只能用平铺的 `ComboBox`／`MultiSelect` 表达 | 数据层级与路径值语义、异步加载（第一版不做）、浮层与键盘模型 |
| 3 | `Transfer` | 多选与全选职责和 `MultiSelect` 重叠，先要证明双列表可见性具有独立价值 | 数据规模、搜索、禁用项、排序与双列表焦点模型；先做与 `MultiSelect` 的职责对照 |
| 4 | `ColorPicker` | 表单输入缺口，但依赖色彩模型与浮层 | 色彩模型与输入格式、对比度提示、浮层与键盘操作 |

本次定调下顺延的候选（保留登记，尚未排序）：

| 候选 | 进入实现前需要明确的问题 |
| --- | --- |
| `Carousel` | 自动播放、键盘模型、触摸手势、内容可见性和 reduced-motion |
| `Image` | 加载、失败回退、预览浮层和媒体资源职责 |
| `QRCode` | 编码实现、纠错级别、SVG/Canvas 输出和依赖策略 |
| `Result` | 与 Empty、Alert、Card 的职责边界 |
| `Anchor` | 滚动容器、活动项判定、历史记录和路由边界 |

排序规则：不以实现成本低作为排序依据；先确认现有组件能否组合完成目标；每项通过 §5 的五道决策门后才进入实现。

## 4. 已评估并暂缓

| 组件 | 结论 | 原因 |
| --- | --- | --- |
| `Table` / `DataGrid` | 暂不做 | 需要先决定只读/排序/分页/编辑职责，以及虚拟化如何与固定行高约束共存 |
| `TreeView` | 暂不做 | 虽可复用 roving-focus，但层级展开、选择、复选和异步加载的公共边界尚未定义 |

暂缓不等于计划中；在完成范围决策前，不得在交付功能或项目索引中列为现有能力。与 §3 中「顺延」的候选不同，此处组件已完成一次范围评估并给出否定结论，不是仅排序靠后。

## 5. 实现决策门

| 决策门 | 通过标准 |
| --- | --- |
| API 边界 | 已说明与现有组件的组合关系、受控/非受控状态、默认值和不支持能力 |
| HTML/ARIA | 已确定根元素、角色层级、键盘模型、焦点模型和错误/禁用/加载语义 |
| Token/主题 | 只消费现有 Token；没有第二套尺寸、颜色、圆角或动效体系 |
| 浮层/JS | 已确认是否复用共享能力；只有必要的浏览器行为才增加 `.razor.js` |
| 示例/验收 | Light、Dark、System、窄屏、键盘和 reduced-motion 有可操作验收路径 |

## 6. 固定交付物

每个公共组件或能力必须同时交付：

1. 组件源码、必要的公开枚举或模型，以及边界校验。
2. 独立可操作示例页，覆盖主要参数、状态和键盘行为。
3. `delivered-features` 的现行 API 与行为记录。
4. 必要的渲染契约、Node 行为回归或真实浏览器断言。
5. `release-history` 的版本交付记录，并从本文件移除已经完成的计划。
6. 按 `AGENTS.md` 改动类型执行的全部门禁结果。

## 7. 状态维护

- 本文件不保存已完成版本的长篇实现过程；任务交付后移入发布历史。
- 审阅发现不复制到本文件；缺陷条目与批次证据只留在审阅计划，本文件不镜像其状态。
- 规划变更不等于公共承诺；只有源码、示例、验证和交付功能全部同步后才算交付。
